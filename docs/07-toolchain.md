# 07 — Gowin toolchain and FPGA workflow

You already have HDMI running on this board, so Gowin EDA install, licensing and
basic bitstream loading are solved and not covered here. This doc covers the
toolchain work this *specific* project adds, and where it lands in the phases.

Flagged throughout: things I could not verify from documentation and you should
confirm in the tool or on the board.

retyping it — a mismatched suffix produces confusing timing results.

## Clocking — getting 2.4576 MHz out of a 27 MHz board

The M100 runs at 2.4576 MHz. 27 MHz is not an integer multiple of it
(27 / 2.4576 = 10.986…), so there are three routes:

### Option 1 — NCO clock enable at 27 MHz (recommended)

Keep the whole design in **one 27 MHz clock domain** and gate CPU advancement
with an enable pulse generated by a fractional accumulator:

```
increment = round(2.4576e6 / 27e6 * 2^32) = 390_937_468
```

A 32-bit accumulator adding that value each 27 MHz cycle, using the carry-out as
the CPU clock enable, yields **2,457,600.0022 Hz — 0.0009 ppm long-term error**.
Individual cycles jitter by one 27 MHz period (37 ns); nothing in this machine
cares, including the UART, because its baud clock is derived from the 81C55
timer counting CPU cycles, so long-term average is what sets baud accuracy.

Why this is the right default: **no clock domain crossing anywhere.** Your bus
sequencer must stretch CPU cycles regardless, and it becomes trivial when the
sequencer runs at 27 MHz and simply withholds the enable. Every timing analysis
question collapses to one `create_clock`.

### Option 2 — MS5351 programmed over I²C

The board carries an MS5351 clock generator. Program it to 24.576 MHz, divide by
10, get an exact clock. **Costs you an I²C master, a bring-up sequence that must
run before the CPU starts, and a second clock domain.** ⚠ I have not verified
which FPGA pins the MS5351's I²C lines land on, or whether it needs
reconfiguring at every power-up. Not worth it unless Option 1 somehow disappoints.

### Option 3 — rPLL to an approximate frequency

Synthesise something near 2.4576 MHz directly. Simplest to describe, worst
accuracy, and it wastes your remaining PLL. Skip it.

## ROM and RAM in BSRAM

**ROM initialisation is the one place where Gowin's flow will waste your time if
you improvise.** Two routes:

1. **IP Core Generator → pROM/pROMX, initialised from a `.mi` file.** Reliable,
   and the route I would take. You will write a converter — `tools/rom2mi.py`,
   32 KB binary in, Gowin `.mi` out. Do this in Phase 0, not Phase 3, so it is
   proven before the core depends on it.
2. **`$readmemh` inference in Verilog.** Sometimes works, sometimes silently
   produces an uninitialised block, depending on version and coding style. ⚠ If
   you try it, verify by reading back a known ROM byte through your HDMI debug
   console before trusting it.

RAM is a plain inferred 32K×8 block, no initialisation needed — but note the
Model 100 quirk your emulator already models: unpopulated RAM reads `0xFF`, and
the ROM sizes memory at boot. Populate all 32K and it never notices.

**Phase 0 standalone experiment, before any CPU exists:** load the ROM into
BSRAM, read a handful of known bytes out through the HDMI console or UART, and
compare against the file. That single experiment removes ROM-init doubt from
every later phase.

## Physical constraints (`.cst`) — the parts specific to this project

```
IO_LOC  "lcd_d[0]" <pin>;
IO_PORT "lcd_d[0]" IO_TYPE=LVCMOS33 DRIVE=8 PULL_MODE=NONE;

IO_LOC  "kbd_row[0]" <pin>;
IO_PORT "kbd_row[0]" IO_TYPE=LVCMOS33 PULL_MODE=UP;
```

Three project-specific points:

- **Keyboard rows use internal pull-ups** — `PULL_MODE=UP`. That is what makes
  the direct-drive keyboard (D4) work with no external resistors. Verify the
  pull-up strength is adequate against the matrix; if scanning is marginal,
  external 10k pull-ups are the fix, not a stronger drive.
- **Use the lowest `DRIVE` that works on everything facing the panel harness.**
  You are driving 400 mm of unshielded wire (R4b) into 1980s CMOS through series
  resistors. Start at `DRIVE=8`, and if you see ringing on the analyzer, drop it.
  Fast edges buy you nothing here; the panel's timing budget is measured in
  hundreds of nanoseconds.
- ⚠ **Set unused/dual-purpose pins to input tri-state in Project Settings.**
  This bears directly on R10: during FPGA configuration the I/O must not drive
  the panel. Confirm the actual default in your Gowin version rather than
  assuming — and belt-and-braces it with the translators' OE pins resistor-pulled
  to the safe state, so the panel sees high-impedance until the design
  deliberately enables it.

## Timing constraints (`.sdc`)

- One `create_clock` on the 27 MHz input if you take Option 1. That is nearly the
  whole file.
- **The busy-flag readback from the panel is asynchronous to your clock.** Two-FF
  synchroniser, and `set_false_path` on the input. Do not let it go straight into
  the sequencer's state logic.
- Timing closure is not expected to be interesting at 27 MHz on a device this
  size. If it is, something is wrong with your design rather than with the tool.

## Programming flow

| Situation | Command | Notes |
|---|---|---|
| Iterate (Phases 1–6) | `openFPGALoader -b tangnano20k impl/pnr/<proj>.fs` | SRAM load, volatile, fast |
| Finished machine (Phase 7) | `openFPGALoader -b tangnano20k -f impl/pnr/<proj>.fs` | Writes external QSPI NOR so the machine boots with no PC attached |

⚠ **Verify flash programming early — do not discover it in Phase 7.**
openFPGALoader's issue tracker carries reports of CRC/ID-verify failures and
hangs when writing flash on Tang Nano boards
([#511](https://github.com/trabucayre/openFPGALoader/issues/511),
[#241](https://github.com/trabucayre/openFPGALoader/issues/241)). It may be fine
with your version and board revision. Flash a trivial blinky in Phase 0, power
cycle with nothing attached, confirm it comes up on its own. If openFPGALoader
misbehaves, Gowin Programmer is the fallback.

This matters more than usual because the end state is a machine in a closed case:
**a design that only exists in SRAM is not a finished machine.**

## On-chip debug (GAO)

Gowin's on-chip analyzer earns its keep in Phases 4 and 5, because it sees what
your external logic analyzer cannot: the CS mask *as the fabric computed it*, the
READY handshake, the sequencer state, and the CPU's port writes — all before they
reach a wire.

The diagnostic triangle for Phase 5 is worth stating explicitly:

| GAO (internal) | HDMI shadow | Real panel | Conclusion |
|---|---|---|---|
| correct | correct | wrong | Wiring, level shifting, bias, or harness |
| correct | wrong | wrong | Bridge logic — CS decode, pointer, page |
| wrong | wrong | wrong | CPU core or 8155 model |

Costs BSRAM for the capture buffer (you have headroom) and a live JTAG
connection, which is fine on the bench and awkward once the case is shut — another
reason the HDMI debug header survives into the finished machine (D6).

## Simulation and the verification harness

This is the part that decides whether Phase 3 takes 35 hours or 80.

- **Build the trace harness before the core is finished, not after.** A Verilator
  or Icarus testbench that runs the real ROM out of a memory model and dumps
  `(pc, a, bc, de, hl, sp, flags)` per instruction, in exactly the format your
  instrumented `cpu85.py` emits. Diff. First divergence names the instruction.
- Make it a one-command target. `make trace && diff` beats any waveform for
  finding a wrong AC flag on `DAA`.
- Use waveforms (GTKWave) for the bus sequencer in Phase 4, where the question is
  timing rather than semantics, and assert HD44102 setup/hold directly in the
  testbench so violations fail loudly in simulation instead of subtly on glass.
- Gowin's built-in simulator: fine for a quick sanity check, not where you run
  millions of instructions.

## Repository hygiene

- **Commit:** HDL sources, `.cst`, `.sdc`, IP generator config, `tools/rom2mi.py`,
  the Makefile, and the openFPGALoader invocations.
- **Do not commit:** `impl/` output, generated bitstreams, and — per this repo's
  standing policy — **the ROM image or anything derived from it, including the
  generated `.mi` file.** `.gitignore` already covers `*.rom` and `*.bin`; add
  `*.mi`, `impl/`, and `*.fs` when you start.
- **Record the Gowin EDA version in the repo.** Bitstream results shift across
  versions, and in six months you will want to know which one built the working
  machine.
